# Tonight's controlled verification

This build was validated with synthetic CSVs and simulated APEX responses. The current workspace contained no supplied company CSVs, screenshots, exports, or saved APEX HTML. Existing repo code supplied the APEX selector/column contract; historical README row counts were not treated as current facts. No authenticated Oracle session or physical Windows scanner was accessible.

1. With the scanner disconnected, run SETUP.cmd. Copy original CSVs into workspace and rerun setup/preflight. Confirm headers and file count. Keep original copies elsewhere as well.
2. Configure the actual scanner and scan one known serial in investigation-only mode. Confirm capture, matching CSV row(s), your login, timestamp, unmodified other fields, and byte-for-byte pre-write backup. Scan again and confirm refreshed last-seen with one first-seen entry. Verify an asset ID maps to the same serial.
3. Test with another application focused. COM should capture without typing there. Windows HID should capture, but also emits keyboard input there. Select only the scanner device; ordinary keyboard typing must not create receipts. Confirm capture survives closing Firefox and reconnects after scanner unplug/replug. Check START.cmd after reboot.
4. In APEX select SPA1 and remove report filters. Connect. Check loaded total and serial index against the actual report. `fetchAll` loads the current report; it cannot override server filters, authorization, or hidden report scope. Unknown rows remain blocked.
5. Scan a known already-staged serial. No new submit or row should appear. Scan one known not-audited serial. Confirm the page's own Enter dynamic action stages the **same existing row**, the model has no unsaved edits, and its saved status is exactly `Staged for Audit`, `Audited`, or `Finalized`. Verify the official counters manually. The connector submits `SERIAL_NUMBER`, using `ASSET_TAG` and `SCANNED_ASSET_SERIAL` as lookup aliases.
6. Validate the application's return-code meanings. This connector treats 2/3/4/7/8/9 as exceptions, but never treats any return code alone as proof of success. If the app uses different names/statuses/events, stop and adjust the documented adapter contract.
7. Disconnect the network during one controlled submission, restore it, then reconnect. It must reconcile without another submission. If the website did not persist the result, the scan must stay in review. Do not repeatedly scan to force success.
8. Scan a product barcode and an unrelated barcode. Neither should alter the official grid. Ambiguous aliases must require review. Test automatic deletion only in an authorized test environment: production persisted rows are never automatically deleted.
9. Walk a short batch while the site is slow. Confirm captured count increases while audit pending accumulates. Close/reopen the station and Firefox separately. Confirm receipts remain and final reconciliation catches any changed statuses.
10. Disable device capture, resolve documented exceptions, and run reconciliation. Complete the official audit separately.

Do not infer production compatibility from the mock. In particular, verify native host registration, scanner keyboard layout/suffix, COM baud, actual APEX metadata persistence, column names, report filters, status vocabulary and dynamic actions. Windows-specific code is included with CI coverage, but a hosted Windows runner has no physical scanner or company browser session.
